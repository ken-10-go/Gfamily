# 日本独自の家系図作成・管理アプリ 開発ロードマップ ＆ タスクバックログ (GitHub Issues 互換)

本ドキュメントは、AIコーディングエージェント（Claude Code、Cursor等）や開発チームが自律的かつ段階的に実装を進められるよう、3つのフェーズに分割した開発ロードマップ、および具体的なGitHub Issue形式のタスクバックログを定義した設計・開発実行プランです。

---

## 開発ロードマップ概要

| フェーズ | 開発マイルストーン（目標） | 主な実装スコープ |
| :--- | :--- | :--- |

## Phase 1: コア基盤 ＆ 単一ツリーセキュアMVP
このフェーズでは、認証、ローカルでのEnd-to-End暗号化、および「1つの家」における基本的な家系図の構築・描画を安定して行えるようにします。

### [Issue #1.1] 認証基盤 (Firebase Auth) と Trees コレクションの構築
*   **概要**: ユーザーがアカウントを作成し、自分専用の家系図ツリー（Tree）を立ち上げるための基本認証機能とメタデータ管理を実装する。
*   **技術要件**:
    *   Firebase Auth (Email, Apple, Googleサインイン等)
    *   Firestore コレクション `trees` の作成
    *   ツリー作成時に、E2EEで鍵導出に使用するための16バイト以上のランダムなソルト（Base64）を自動生成し、ツリーのメタデータとして非暗号化領域（`salt`）に保存する。
*   **受け入れ基準 (Acceptance Criteria)**:
    *   ユーザー登録/ログインが成功し、UIDが取得できること。
    *   初回ログイン時、新規のツリーが1つ作成され、メタデータとして一意の `salt`（Base64形式文字列）がDBに書き込まれること。

### [Issue #1.2] クライアントサイドE2EE (AES-256-GCM / PBKDF2) 暗号化モジュールの実装
*   **概要**: ユーザーが設定したツリー用パスフレーズからセキュアに暗号鍵を導出し、個人情報の機微データを暗号化・復号するクラスをDartで実装する。
*   **技術要件**:
    *   `package:cryptography` パッケージの使用
    *   `PBKDF2` (iterations: 100,000, HMAC-SHA256, derivedKeyBits: 256) を用いた鍵導出
    *   `AES-256-GCM` による暗号化/復号
    *   バックアップ用のリカバリPDF（QRコードにパスフレーズをエンコード）の自動生成ロジックの定義
*   **受け入れ基準**:
    *   同一のパスフレーズとソルトから、常に一意の同じ `SecretKey` が導出されること。
    *   「本籍地」「旧姓」「エピソード」等のプレーンテキストを暗号化し、`encryptedData`, `iv`, `tag` を含むMapが生成されること。
    *   異なるパスフレーズで復号を試みた際に、自動的に例外（認証タグ検証エラー）がスローされ、復号が安全にブロックされること。

### [Issue #1.3] 基本的な人物(Persons)と関係性(Relationships)のCRUD ＆ モデル層実装
*   **概要**: 家系図の登場人物、および「実親子」「養親子」「婚姻」などの関係を管理するためのモデルクラスとFirestoreリポジトリを実装する。
*   **技術要件**:
    *   `persons` サブコレクション、`relationships` サブコレクションのデータモデル（Dart）
    *   生存者データ保存時の自動暗号化処理、故人データ保存時のプレーンテキストフォールバック処理の組み込み
    *   不完全な生没年月日（年、月、日のNullable保持）をパースする入力インターフェースへの対応
*   **受け入れ基準**:
    *   生存者として人物を追加した際、Firestore上に本籍地や住所がE2EE暗号化されたMap形式で保存されること。
    *   故人（`isDeceased = true`）として保存した場合は、他家との共同供養・共有のためプレーンテキストフィールドに透過的に保存されること。

### [Issue #1.4] 縦横ダイナミック・トグル描画と InteractiveViewer による基本家系図UI
*   **概要**: Flutterの `InteractiveViewer` と `CustomPainter` を用い、人物ノードと関係のエッジ線をスマホ画面にスムーズに描画・ズーム・パンできる基本UIを実装する。
*   **技術要件**:
    *   縦書き（右から左へ、上から下へ直系線を引く折本スタイル）と、横書き（水平階層スタイル）のトグル切り替えUI
    *   実親子（一本実線）、婚姻（二重実線）、養親子（破線）のCustomPainterによる描画
*   **受け入れ基準**:
    *   画面上の切り替えスイッチを押すことで、家系図の描画方向（縦書き・横書き）がカクつくことなく瞬時に切り替わること。
    *   ピンチイン・ピンチアウトによる拡大縮小、およびドラッグによるキャンバスのスクロールが滑らか（60fps以上）に動作すること。

## Phase 2: 複数ツリー接続 ＆ セキュア共同編集
このフェーズでは、オンラインデータベースの優位性を活かし、親族間でのリアルタイム共同編集、他家とのブリッジ連携、そして生存者の徹底的な隠蔽をセキュリティルール（Firestore Rules）で自動担保します。

### [Issue #2.1] 本番対応 Firestore Security Rules のデプロイとテスト実装
*   **概要**: データベース直通のセキュリティルールを記述し、他人のツリーからの不正アクセス、および結合ツリー時の生存者データの漏洩を物理的に遮断する。
*   **技術要件**:
    *   `firestore.rules` の実装
    *   `@firebase/rules-unit-testing` を用いたセキュリティテストコード（TypeScript）の構築と検証
*   **受け入れ基準**:
    *   ツリーに招待されていない未認証ユーザーの読み書きリクエストが、ルール層で全て `Permission Denied` になること。
    *   後述する「ブリッジ接続（active）」がある状態でも、生存者のデータ読み取りは拒否され、故人データ（`isDeceased == true`）の読み取りのみが成功すること。

### [Issue #2.2] ダブル・ハンドシェイク（相互承認）ブリッジ機能とCloud Functionsの実装
*   **概要**: 山田家と佐藤家のツリー所有者同士が承認し合うことで、双方の家系図を安全に論理接続するトランザクション処理を実装する。
*   **技術要件**:
    *   Firestore `treeBridges` コレクションの監視
    *   Cloud Functions (TypeScript) による `acceptBridgeConnection` 関数の実装（アトミックな承認とステータスの "active" 更新）
*   **受け入れ基準**:
    *   A家がB家にブリッジ申請（status: pending）を出した段階では、まだお互いの家系図は結合表示されないこと。
    *   B家のOwnerが承認ボタンを押し、`approvedBy` 配列に自身のUIDが書き込まれた時点で status が自動的に `active` に更新されること。
    *   どちらか一方がブリッジを削除（delete）した際、即座にお互いの参照権限が失効すること。

### [Issue #2.3] ダイナミック・フォーカス ＆ インテリジェント・ビューポート制限
*   **概要**: 結合された巨大な家系図でもスマホ画面がノードで埋め尽くされないよう、選択した人物を中心に関係のある親族（祖先3代・子孫3代など）だけを抽出して描画する機能を実装する。
*   **技術要件**:
    *   ダブルタップされたノードを画面中央に1000msでアニメーション移動する `InteractiveViewer` の制御
    *   フォーカス中の人物IDを起点に、指定深度（depth）内のPersonとRelationshipのみを再帰的探索でフィルタリングするローカルロジック
*   **受け入れ基準**:
    *   人物をダブルタップした際、その人物が画面中央にズーム移動し、不要な遠縁のカードが自動的に画面上からフェードアウト（または非表示）になること。

## Phase 3: 文化的機能の統合 ＆ 描画パフォーマンス最適化
最終フェーズでは、日本の伝統的な年中行事や供養をデジタルで優しくサポートするロジックの実装と、大量の親族カードを動かしてもカクつかないレンダリングの最適化を行います。

### [Issue #3.1] 仏教回忌法要・伝統行事自動計算 ＆ LINE/FCM通知 Functions
*   **概要**: 故人の没年月日をもとに、お盆・お彼岸・回忌法要（一周忌、三回忌、七回忌、三十三回忌等）を自動計算し、親族メンバーへ自動通知するバックエンド処理を実装する。
*   **技術要件**:
    *   Cloud Functions Pub/Sub 予定トリガー（Cronスケジュール：毎日AM 9:00実行）
    *   日本の伝統的な回忌計算アルゴリズムの組み込み
    *   Firebase Cloud Messaging (FCM) または LINE Messaging API との連携
*   **受け入れ基準**:
    *   今年、回忌法要を迎える故人がツリー内にいる場合、特定の親族ユーザーに対して「今年は〇〇様の十三回忌にあたります（お盆/お彼岸通知）」といったプッシュ通知が正常にトリガーされること。

### [Issue #3.2] 家紋マスター（8,000種）および名字ルーツ検索の統合
*   **概要**: ユーザーが自身の名字のルーツを検索したり、家のシンボルである「家紋」をマスターデータから選択して家系図のトップや人物カードの背景・プレースホルダーに設定できる機能を実装する。
*   **技術要件**:
    *   家紋画像（SVG/ベクター）のアセット管理、キーワード検索API
    *   顔写真のない先祖に対して、家紋、または名字ルーツをモチーフとした和風イラスト（フォールバック画像）を動的に割り当てるUIコンポーネント
*   **受け入れ基準**:
    *   「キーワード（例：丸に、鶴）」で検索した際に適合する家紋の一覧が表示され、タップで人物のプロフィール写真の代わり、あるいはツリー全体のロゴとして設定できること。

### [Issue #3.3] ドラッグ操作時の描画パフォーマンス最適化（RepaintBoundary ＆ 楽観的更新）
*   **概要**: ノードを左右にドラッグして兄弟姉妹の並び順（sortOrder）を入れ替える際、画面が一切カクつかず（120Hz/60fps維持）、かつFirestoreへの無駄な書き込みを徹底的に削減する。
*   **技術要件**:
    *   ドラッグ対象となる `FamilyPersonCard` への `RepaintBoundary` の適用
    *   ドラッグ中の座標変更に伴うエッジ（関係線）の軽量化（直線での描画）と `ValueNotifier` による局所的な状態管理
    *   Firestoreへの `WriteBatch` を用いた、ドラッグ確定時のアトミックな一括書き込み（デバウンス、または OnDragEnd タイミング）
*   **受け入れ基準**:
    *   人物カードを長押しドラッグし、左右の兄弟カードとスワップ（並び替え）する際、UIが全く引っかかることなく滑らかに動作すること。
    *   ドラッグを離した（静定した）タイミングで、変更された兄弟の `sortOrder` だけが1回のバッチ処理でまとめてFirestoreに反映され、それ以外の不要な読み書きリクエストがトリガーされないこと。
