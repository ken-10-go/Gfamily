# 日本の文化的要求を反映した家系図作成・管理アプリ「絆ツリー (Kizuna Tree)」機能要件定義書 (Requirements v4)

本ドキュメントは、**Claude Code等のAIコーディングエージェント**に直接インプットし、フロントエンド（Flutter/React等）およびFirebaseバックエンド（Firestore, Auth, Storage, Functions）のソースコードやテストコードを即座に自動生成させるための、極めて詳細かつ厳格な機能要件定義書（PRD）である。

---

## 1. プロダクト概要

### 1.1 背景とビジョン
既存のグローバル系図サービス（FamilySearch [5], MyHeritage [7] など）は、世界中のユーザーが「一つの巨大な世界樹」を共同編集する設計が一般的である [35, 98]。しかし、これは日本の家制度やデリケートな親族関係において、意図しないデータの書き換えや、生存者の極めて機微な個人情報（旧姓、本籍地など）の意図しない漏洩を招くリスクが高い [148]。
本プロダクト「絆ツリー」は、**「家（ツリー）ごとの論理的隔離」と「オンラインリアルタイム親族共同編集」を、Google Cloud / Firebaseのサーバーレス環境を用いて極めて低コスト（基本無料）かつゼロトラストセキュリティで両立させる、日本市場に特化した家系図作成・管理アプリケーション**である。

### 1.2 本アプリが解決する日本特有の文化的・実務的課題
1.  **戸籍・先祖調査との親和性**: 日本の戸籍調査（除籍謄本、改製原戸籍等の解読）で判明する「本籍地」「旧姓」「旧字体・変体仮名」を正規カラムとして扱い、先祖探しの実用に耐えうる仕様とする [1, 3, 149]。
2.  **不完全な歴史的日付の管理**: 「享保◯年 月日不明」「年号しか判明していない」といった、西暦に完全変換できない日付データを、DB並び替えや系統描画を破綻させずにそのまま保存・表示可能とする [122, 133]。
3.  **仏教・葬送文化との融合**: 「戒名（法名・法号）」や「お墓の位置情報」「デジタル過去帳」「回忌法要」を人物プロファイルおよび供養機能として一元管理する [144, 156, 158]。
4.  **名字と家紋のアイデンティティ**: 日本全国の名字の由来解説データベース、および家紋選択・検索マスターと連動し、一族のアイデンティティを視覚化する [124, 130]。
5.  **複雑な親族・養子縁組のビジュアル化**: 婿養子や家督相続に伴う複雑な「養子縁組（実家と養家の二重帰属）」や「再婚」「いとこ婚」を破綻なく描画する [127, 131]。

## 2. アカウントとロール定義 (アクセス制御)

アプリ内では、家系図の単位を「ツリープロジェクト（以下、ツリー）」と呼ぶ。各ツリーに対して、以下の3つの役割（Role）を厳格に割り当てる。

| ロール | 権限範囲 | 具体的なアクション |
| :--- | :--- | :--- |
| **Owner (所有者・家長)** | フルアクセス権 | ツリーの新規作成、削除。Editor/Viewerの招待・権限変更・削除。生存者/故人の全データの読込・書込。他家（他ツリー）との接続（ブリッジ）承認・解除権。E2EEパスフレーズの決定。 |
| **Editor (共同編集者・親族)** | データ編集権 | 生存者/故人の人物カードの追加、削除、属性編集。関係線（親子・婚姻）の追加・削除。ツリー設定の閲覧。※他ツリーとのブリッジ操作、およびメンバーの管理権限は持たない。 |
| **Viewer (閲覧者・親族)** | 閲覧専用権 | ツリー内の生存者/故人データの閲覧。家系図描画ビュー、人物票、イベント年表の閲覧。※データの追加・編集・削除、E2EE暗号化データの生テキスト復号（権限付与がない限り）は不可。 |

## 3. 機能要件 (Functional Requirements)

### 3.1 日本固有の人物プロファイル（属性）管理機能

各人物（`Person`）の登録カードにおいて、以下の属性項目を入力可能とする。

#### 3.1.1 必須項目
*   **姓 (Last Name)** & **名 (First Name)**: 旧字体・変体仮名等のマルチバイト文字を許容。
*   **よみ (Kana)**: 名字・名前の「よみ（かな）」を入力可能とし、並び替えの基準とする [142]。
*   **性別 (Gender)**: Male (男性) / Female (女性) / Other (その他、または多様な家族表現用)。
*   **生存ステータス (is_deceased)**: `Boolean`。故人の場合は「故人グレー背景」等の表示切り替えに使用する [3, 131]。

#### 3.1.2 文化的・実務的補足項目 (任意入力 / ゼロトラスト暗号化対象)
*   **旧姓 (Maiden Name)**: 婚姻前の名字。検索・表示上で明示的に管理 [61, 148]。
*   **本籍地 (Honseki)**: 都道府県から番地まで。戸籍取得・解読履歴と紐付け。**【E2EE対象】** [1, 3]
*   **現住所 (Address)**: 存命人物の連絡用。**【E2EE対象】** [1, 3]
*   **戒名 / 法名 / 法号 (Kaimyo)**: 仏教・葬送供養における没後名。宗派に応じた入力をサポート。**【E2EE対象】** [144]
*   **お墓情報 (Grave Location)**: 写真、地図（緯度経度）、霊園名、墓石に刻まれた文字などのメモ。**【E2EE対象】** [158]

#### 3.1.3 日付管理（西暦・和暦ハイブリッド仕様）
生年月日（`birth_date`）および没年月日（`death_date`）は、以下の3パターンでの登録を許容する仕様とする：
1.  **完全日付**: 西暦および和暦（元号＋年＋月＋日）を相互変換して保存。
2.  **不完全日付（月日不明など）**: 例：「1852年（嘉永5年） 月日不明」や「明治10年 年月日不明」など。DB上には数値型の `year`, `month`, `day` を個別に持ち、月日を `null` または `0` として許容する [122, 133]。
3.  **和暦文字列**: 元号一覧マスター（明治、大正、昭和、平成、令和、および江戸時代以前の主要元号：慶応、元治、文久、万延、安政、嘉永、弘化、天保など）から選択入力された生データをそのままテキスト保持。

### 3.2 複数家（マルチツリー）管理と「ダブル・ハンドシェイク」統合機能

本アプリの最大の差別化機能であり、Claude Codeに厳格な実装を求める部分である。

1.  **個別ツリーの隔離**: A家（Owner: User_A）とB家（Owner: User_B）は、デフォルトで完全に異なるドキュメント空間に存在し、相互にデータを見ることはできない。
2.  **接続（ブリッジ）の申請**: User_Aが、自ツリーの特定の人物（例：娘）と、User_Bのツリーの特定の人物（例：夫）を婚姻関係として接続したい場合、アプリ上で「接続招待リンク」または「ワンタイムトークン」を発行する [56]。
3.  **双方向承認（ダブル・ハンドシェイク）**: User_Bがその招待を受け入れ、接続先を承認してはじめて、システム内に `TreeBridge` レコードが作成される。
4.  **結合（マージ）ビューの描画**:
    *   ブリッジが成立すると、A家とB家の家系図が画面上で統合され、地続きの1つの巨大なツリーとして描画される [126]。
    *   ただし、実データがA家とB家で直接マージされるわけではなく、ビューポートが両ツリーのデータを動的に結合して描画する。
    *   **生存者保護**: 統合描画時であっても、A家のメンバーに対しては、B家の「生存者」の機微情報（詳細プロファイル）は表示せず、「B家の生存者（プライバシー保護のため非表示）」または「男性」「女性」といったダミーカードとして描画する。故人の情報は、設定された共有権限に基づき、戒名やお墓、思い出話を相互に閲覧・供養できるようにする。
5.  **ブリッジの即時解除**: どちらか一方のOwnerがブリッジ接続を「解除」した場合、データベース内の `TreeBridge` レコードは即時物理削除され、両ツリーの接続表示およびアクセス権は一瞬で遮断される。データが相手方に残ることはない。

### 3.3 日本の風習・伝統行事連携（Cloud Functionsバッチ）

ユーザーが登録した生年月日・没年月日データに基づき、日本独自の節目となるタイミングで親族に通知を送る。

1.  **回忌法要自動算出と命日通知**:
    *   故人の「没年月日（命日）」から、今年が何回忌（一周忌、三回忌、七回忌、十三回忌、十七回忌、二十三回忌、二十七回忌、三十三回忌、五十回忌など）にあたるかを毎日自動判定する [131, 145]。
    *   祥月命日の30日前、お盆（7月/8月）の15日前、お彼岸（春分・秋分の日）の7日前に、関係するツリーのメンバー全員へ、プッシュ通知またはLINE通知を自動配信する [131]。
2.  **長寿の祝いと厄年・干支の自動算出**:
    *   生存者の生年月日をもとに、以下の伝統的ライフイベントが近づいた際に通知を送る [132]。
        *   **長寿の祝い**: 還暦（61歳）、古希（70歳）、喜寿（77歳）、傘寿（80歳）、米寿（88歳）、卒寿（90歳）、白寿（99歳）、百寿（100歳）
        *   **節目の行事**: 七五三（3歳・5歳・7歳）、成人、厄年（男性：25/42/61歳、女性：19/33/37/61歳の大厄および前厄・後厄）
        *   **干支**: 年男・年女（12年に一度の生まれ年の干支の巡り） [132]

### 3.4 名字・家紋データベース連携

1.  **名字由来検索機能**:
    *   人物プロファイルで入力された「姓」をもとに、名字由来データベースAPI（またはマスターテーブル）を検索。
    *   その名字の起源（発祥の地、歴史的背景）、全国におけるおおよその人数、都道府県別の分布順位などの情報を、人物詳細画面の「名字のルーツ」タブに自動表示する [123, 124]。
2.  **家紋登録・検索機能**:
    *   日本全国に存在する主要な家紋（8,000種以上のモチーフデータ [53, 54]：丸に木瓜、丸に片喰、丸に抱き茗荷、源氏車など）を、キーワードや武将名、デザインのモチーフ（植物、動物、幾何学）から検索。
    *   自分の家の家紋を選択すると、家系図のトップヘッダーや、故人のカード背景に美しくレンダリングされる [53, 127]。家紋の歴史的意味や由来の解説も閲覧可能 [53, 124]。

### 3.5 日本の様式美を尊重した家系図描画（UI/UX要件）

1.  **縦書き（折本形式）と横書き（デジタル形式）の動的切り替え**:
    *   **縦書きビュー**: 日本の伝統的な「和装表紙・折本形式（右から左へ世代が進み、縦に文字が流れる）」の様式美をCSS GridやSVGを用いてブラウザ/アプリ上に再現する [28, 168]。
    *   **横書きビュー**: デジタルデバイスで見やすい、上から下へ、または左から右へ世代が進むフラットレイアウト。
2.  **フォーカス中心ツリー（Dynamic Node Focus）**:
    *   全員を表示すると画面が破綻するため、選択した人物（プロタゴニスト）を常に画面中央に配し、そこから「祖先3世代・子孫3世代」を動的に抽出し、画面外の遠縁はクローズする機能（すいすい家系図 [60] やKeif [3] の思想を踏襲）。
3.  **複雑な関係線のサポート**:
    *   **婚姻（夫婦）**: 二重実線、または伝統的な夫婦を横に並べる「クミ」形式。
    *   **実親子**: 一本実線。
    *   **養親子（養子縁組）**: 破線、または二重細線で表現。実家と養家の双方に線が伸びる「二重帰属」を視覚化し、タップで実家ツリービューと養子先ツリービューをスムーズに切り替え。
    *   **再婚・いとこ婚・同性パートナーシップ**: 関係線が交差して破綻しないよう、再婚相手はスライド切り替えカード、同性関係は設定に基づき適切に等位線で結ぶ [127, 131]。

## 4. 非機能要件 (Non-Functional Requirements)

1.  **無料ベースのサーバーレス実装**:
    *   Firebaseの無料枠（Sparkプラン）を使い切らない極めて軽量なPayloadとスマートなFirestore読み書き設計（キャッシュの活用）を行う。
2.  **オフライン対応（ローカルキャッシュ同期）**:
    *   親戚の集まりや、お墓参り、先祖ゆかりの地方自治体での戸籍調査など、電波の届きにくい場所でも閲覧・編集ができるよう、Firestoreの「Offline Persistence」を標準で有効化する [39, 163]。
3.  **エクスポートと長期保存（保存性の担保）**:
    *   家系図アプリ最大の消失リスク（サービス終了 [148, 150]）に備え、以下の2形式でのエクスポートを必須とする：
        *   **標準PDF形式**: 印刷して仏壇や実家に物理保管できる、折本サイズに対応した印刷用レイアウトPDF出力（KeifのPDF出力 [1], 名字由来netのPDF出力 [127], 人物票作成アプリ [164] などの標準仕様）。
        *   **JSON/CSVポータビリティデータ**: 他の系図ソフト（エクセルや親戚まっぷ [40] 等）にインポートできるよう、国際標準規格であるGEDCOM形式、または一般的なCSV形式でのエクスポートをサポート [44]。
