# 「絆ツリー (Kizuna Tree)」クライアントサイドE2EE（エンドツーエンド暗号化）＆セキュリティ技術仕様書 (Security Specs v3)

本ドキュメントは、**Claude Code等のAIコーディングエージェント**が、モバイル・Webフロントエンド（Dart/TypeScript）において、本籍地や戒名、現住所などの超機微個人情報を暗号化する「暗号化・復号ヘルパークラス（Helper Class）」を堅牢に自動生成し、セキュリティテストを実装するための詳細な技術仕様書である。

---

## 1. ゼロトラストE2EEの設計方針

本システムでは、ユーザーの重要なプライバシー（本籍地 [1, 3]、現住所 [1, 3]、戒名 [144]、お墓の位置 [158]、詳細メモ [157]）を保護するため、「サーバー運営者（Google Cloudおよびアプリ開発元）であってもデータを絶対に解読できない」**ゼロトラスト（End-to-End Encryption - E2EE）モデル**を採用する。

*   **暗号化処理の境界**: すべての暗号化および復号は、ユーザーの**クライアント端末（モバイルアプリ、またはブラウザ）のメモリ（RAM）上**で行われる。
*   **平文（デコードデータ）の不保持**: クラウドデータベース（Firestore）には、暗号化済みの文字列（Ciphertext）と初期化ベクトル（IV）、およびMAC（認証タグ）のみが送信・保存され、平文の機微データはネットワーク上を一切流れない。
*   **パスフレーズの非保存**: 暗号鍵の生成元となる「親族の合言葉（パスフレーズ）」は、FirestoreやAuthなどのバックエンドには決して保存されない。ユーザーの端末内にのみ、一時的に保持（セッション有効期間中）される。

## 2. 鍵導出ロジック (Key Derivation Function: KDF)

ユーザーが入力したパスフレーズから、AES-256ビット暗号化に耐えうる強力な対称鍵を生成する。

### 2.1 パラメータ仕様
AIコーディングエージェントが、標準的な暗号ライブラリ（Flutterの `pointycastle` やWebの `Web Crypto API`）を用いてキー生成コードを実装するための固定値。

| パラメータ名 | 技術規格 | 設定値 | 目的 |
| :--- | :--- | :--- | :--- |
| **アルゴリズム** | **PBKDF2** | `HMAC-SHA256` | パスフレーズからのセキュアなストレッチング鍵導出 |
| **ストレッチング回数 (Iterations)** | `number` | `100,000` 回 | 総当たり（ブルートフォース）攻撃への耐性担保 |
| **導出鍵長 (Key Length)** | `bit` | `256` bit (32 bytes) | AES-256に対応する十分なエントロピーの確保 |
| **ソルト (Salt)** | `Base64 String` | 32 bytes (ランダム生成) | レインボーテーブル攻撃の防止。`/trees/{treeId}.e2eeSalt` から取得。 |

### 2.2 鍵導出フロー（シーケンス）
1.  **ツリー作成時**:
    1.  クライアント端末側でセキュアな疑似乱数生成器（CSPRNG）を用いて 32 bytes の `e2eeSalt` をランダム生成。
    2.  `e2eeSalt` を Base64 文字列に変換し、平文で `/trees/{treeId}` ドキュメントに保存（これは公開されても問題ない）。
2.  **アプリログイン時 / ツリーロード時**:
    1.  ユーザーに「親族パスフレーズ」の入力を求める。
    2.  当該ツリーの `e2eeSalt` をFirestoreから読み込む。
    3.  `PBKDF2(passphrase, salt, iterations=100000, keyLength=32)` を実行。
    4.  生成された32バイトのバイト配列を、メモリ上の暗号セッション（RAM）に `AES-GCM-256` 鍵として保持。

## 3. 暗号ペイロード構造 (Encryption Envelope)

暗号化アルゴリズムには、データの秘匿性（Confidentiality）と改ざん検知（Integrity）を同時に保証する、高セキュアな **`AES-256-GCM`** を使用する。

### 3.1 暗号化プロセス
1.  暗号化したい属性オブジェクト（`PersonEncryptedDecrypted`）をJSON文字列化する。
    ```json
    {
      "honseki": "東京都千代田区永田町1-7-1",
      "address": "東京都千代田区永田町1-7-2",
      "kaimyo": "釋大観太郎居士",
      "graveLocation": "青山霊園 3区-25号",
      "biographyNotes": "幼少期は実家の本家で育ち、後に山田家へ婿養子に入る。"
    }
    ```
2.  CSPRNGにより、毎回必ず一意な **12バイトの初期化ベクトル（IV / Nonce）** を生成。
3.  メモリ上の暗号鍵を用いて `AES-GCM` 暗号化を実行。
4.  暗号化結果から、**暗号文（Ciphertext）**と、**16バイトの認証タグ（Auth Tag / MAC）** を取得。
5.  これらをすべて Base64 文字列に変換し、以下の `EncryptedPayload` スキーマ（Firestore上の `encryptedData`）として保存する。

### 3.2 Firestore上の格納形式 (JSON)
```json
{
  "encryptedData": {
    "iv": "dGhpcyBpcyBhbiBhdXRoIGl2",     // 12-byte IV (Base64)
    "ciphertext": "YW5vbnltdXMgY2lwaGVydGV4dCBkYXRh", // 暗号化されたJSON (Base64)
    "tag": "YXV0aGVudGljYXRpb24gdGFn"    // 16-byte Auth Tag (Base64)
  }
}
```

## 4. パスフレーズ紛失時の回復と段階的データ設計

AIエージェントに実装させる際の、最重要エッジケースへの対処ロジック。

### 4.1 パスフレーズを紛失した場合の影響
*   E2EE暗号化された項目（本籍地、住所、戒名、メモ、お墓など）は、数学的に**絶対に復号不可能**となる。
*   しかし、家系図の構築自体を破綻させないため、暗号化されていない「基本情報（姓、名、かな、生没年月日の年部分、性別、生存ステータス）」および「親子・婚姻などの接続関係（`relationships`）」は**そのまま問題なく表示・編集・維持**される。
*   すなわち、「パスフレーズを忘れた場合でも、家系図の形（骨組み）は残り、重要機微情報のみが非表示（ロック）になる」という、実用性を重視した設計とする。

### 4.2 バックアップとパスフレーズのリセット仕様
*   **セキュリティカードのPDFダウンロード**:
    ツリーの初期作成時に、パスフレーズと「緊急リカバリーコード（ランダムな英数字24文字）」を記載した『セキュリティバックアップカード』のPDF（Keif [1] などの印刷機能、人物票作成アプリ [164] のPDF仕様を応用）をユーザーにダウンロードまたは印刷させ、物理的に仏壇や金庫等へ保管することを強く推奨する。
*   **リカバリーコードによる復号鍵の再生成**:
    リカバリーコードが入力された場合、そのコードをハッシュ化した値をPBKDF2の追加ソルトとし、パスフレーズを強制リセットして新しい暗号空間を再構築可能とする。

## 5. セキュリティテストコード（AIへの実装指示）

Claude Code等のAIエージェントに対し、Firebaseエミュレータ（`@firebase/rules-unit-testing`）を用いて、記述したセキュリティルールが完全に動作するかを実証するためのテストケースを作成させる。

### 5.1 必須実装テストケース
1.  **自ツリー内の完全アクセス権テスト**:
    *   `Owner` として認証されたユーザーが、自ツリーの `/persons` や `/relationships` の全データ（生存者・故人）を読込・書込可能であることをテスト。
2.  **他家ツリーの生存者非表示（完全隔離）テスト**:
    *   Aツリーのメンバーである `User_A` が、Bツリー（接続なし）のいかなる生存者/故人データに対しても、Read/Writeアクセスが拒否される（Permission Denied）ことを確認。
3.  **ダブル・ハンドシェイク未完了時の隔離テスト**:
    *   AツリーとBツリーの間で `TreeBridge` のステータスが `pending`（申請中）の時、お互いのデータへの読み込み権限が一切ないことを確認。
4.  **ダブル・ハンドシェイク成立後の「故人限定」共有テスト**:
    *   `TreeBridge` のステータスが `accepted`（承認済み）の時、`User_A` がBツリーの「故人（`isDeceased == true`）」のデータだけを読み込めることを確認。
    *   同時に、Bツリーの「生存者（`isDeceased == false`）」のデータへのアクセスは、依然として遮断されることをテスト。
5.  **ブリッジ接続即時解除テスト**:
    *   `TreeBridge` レコードが削除された瞬間、他家の故人データが即時読み込み不可になることを確認。
